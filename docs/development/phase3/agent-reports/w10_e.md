## Publication checklist owned by root

1. **Freeze and stage only the final intended state.** Wait for the final task
   and all document writers, finish the factual ledger, inspect the final
   scope, and then stage the documentation/evidence changes. Run snapshot
   creation only after this freeze. The helper does not lock HEAD or the index
   across its multiple Git commands, and a snapshot cannot capture unstaged
   or untracked changes that have not been added. These are caller-owned
   preconditions.
2. **Verify the new snapshot identity before transport.** Require parent
   `beedd8bfd1cea3c722409ef0f959fcec5420c5f2`, base tree
   `4da5c68c7e6dbeb13f2e2e04179c2ea5535e390e`, and snapshot tree equal to the
   frozen index's `git write-tree`. Inspect its complete path/mode inventory;
   do not treat the old 92-entry snapshot as the final one. The helper accepts
   only A/M entries and regular modes `100644` or `100755`; unsupported
   deletion, rename, symlink, gitlink, or unresolved-stage changes fail closed.
3. **Reassemble immutable payloads without text conversion.** Read each
   snapshot entry through its recorded blob SHA. Parse the helper's JSON
   string output once and concatenate its contents in order. Chunk offsets
   for UTF-8 entries are Python Unicode character counts, not byte offsets;
   base64 entries use ASCII counts. Check the complete reconstructed byte
   length and Git blob SHA before accepting a payload. Do not read changing
   working-tree files or normalize newlines.
4. **Create binary blobs before their tree entries.** Send gzip bytes as
   base64 with `encoding="base64"` to GitHub `create_blob`, and require every
   returned SHA to equal the corresponding snapshot blob SHA. Put that
   returned SHA, the exact path, and the recorded mode in the tree entry.
   Do not put base64 text in a tree entry's `content` field. For UTF-8 files,
   use the reconstructed Unicode content. Preserve all ten gzip paths even
   though only six distinct binary blob contents exist.
5. **Keep tree batching sequential and verify the full final tree.** Begin
   from the expected candidate base tree. Each subsequent batch must use the
   immediately previous returned tree as its base, so earlier batches are
   retained. Preserve recorded modes and unchanged entries, including the
   existing gitlinks. Require the final API tree SHA to exactly match the
   final local snapshot/index tree before creating or publishing the commit.
   Blob or tree creation alone must never update `main`; partial failures
   therefore leave only unpublished objects and can be retried safely after
   verifying their identities.
6. **Verify and hydrate the exact commit object.** Create the final commit
   with the single parent `beedd8...` and the verified final tree, then check
   the API response's parent list, tree, and SHA. The hydration helper searches
   possible original timezone offsets and both message-final-newline forms,
   and writes an object only when its complete Git hash equals the returned
   remote SHA. It fails closed for signatures or an unmatched reconstruction.
   It assumes the author and committer use the same offset and handles no
   additional arbitrary commit headers; if a new API object violates those
   assumptions, retain the failure and reconstruct the actual object rather
   than substituting a new commit. The candidate's observed equal `-0400`
   offsets fit the helper. Confirm hydrated SHA/tree/parent again.
7. **Use the expected old ref and preserve failure evidence.** Update any
   local branch ref with the expected old value, and perform a fresh remote
   `main` observation immediately before publication. Require the observed
   old ref to equal `beedd8...`, then use the expected-parent, nonforce update
   plan. `force=false` alone is not an exact-old-SHA compare-and-swap: preserve
   the explicit lease/precondition checking in root's flow. If publication
   fails or times out, inspect both refs before retrying; do not assume that a
   locally hydrated/advanced commit has reached the remote. Verify final
   remote/local commit and tree equality after success.
8. **Observe final CI separately and avoid another push while it runs.** All
   four workflows trigger for a push to `main` without a documentation path
   exclusion. Phase 1/2/3 each use a branch concurrency group with
   `cancel-in-progress: true`; repository integrity has no such cancellation
   setting. The retained candidate summary reports all four prior runs as
   completed/success, so those recorded completed runs are not pending work
   that this publication would cancel. A further push during the final
   numerical workflows can cancel the descendant's runs. Observe all four
   final run IDs, exact head SHA, completed status, and success conclusions;
   report that descendant separately from the original acceptance receipts.
