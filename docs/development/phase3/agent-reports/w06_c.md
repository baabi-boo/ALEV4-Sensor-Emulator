## Finding 1 — existing staging directory could be written and recursively deleted

**Status: fixed in the assigned exporter.**

The exporter formed a staging path by appending `.spatial-stage` to `tempname(parent)`, then treated `mkdir` returning `ok=true` as proof that it owned the directory. An unused basename from `tempname` does not imply that the suffixed name is unused. In GNU Octave 9.4.0, `mkdir` on an existing directory returns `ok=true` and `message='directory exists'`.

A bounded fault probe forced `tempname` to return an actually unused base while its suffixed staging directory already contained unrelated sentinel data. The exporter wrote files into that preexisting directory. Its staged reader rejected the extra sentinel under the exact-inventory rule, after which the exporter's cleanup recursively removed the preexisting directory and sentinel. The requested destination remained absent. This is an ownership failure before final publication, not an unsupported destination race.

The reproduction is retained in `w06_c_collision_probe.m`. All affected paths are newly created test-owned temporary paths; no retained artifact was used. Observed output before the fix:

```json
{"runtime":"9.4.0","unused_base_remains_absent":true,"mkdir_existing_ok":true,"mkdir_existing_message":"directory exists","error_identifier":"ALEV4:InvalidSpatialMetadata","error_message":"Bundle directory must have exactly its declared file inventory.","preexisting_stage_preserved":false,"preexisting_sentinel_preserved":false,"destination_absent":true,"rng_preserved":true,"handles_preserved":true}
```

### Implemented change

Immediately after selecting the suffixed staging candidate, `exportSpatialBundle` now rejects any existing entry using `bundlePathExists`, which includes dangling symlinks. It then requires `mkdir` to return both success and an empty message. The recursive cleanup guard and all payload writes are installed only after that unambiguous new creation. The exporter returns `ALEV4:SpatialWriteFailed` when it cannot establish ownership.

The change deliberately rejects a collided candidate rather than silently claiming it or retrying indefinitely. The existing target checks, staged verification and final publication logic remain in place. It makes no new atomicity or concurrent-writer promise.

The identical reproduction after the fix produced:

```json
{"runtime":"9.4.0","unused_base_remains_absent":true,"mkdir_existing_ok":true,"mkdir_existing_message":"directory exists","error_identifier":"ALEV4:SpatialWriteFailed","error_message":"Cannot claim an existing staging path.","preexisting_stage_preserved":true,"preexisting_sentinel_preserved":true,"destination_absent":true,"rng_preserved":true,"handles_preserved":true}
```

## Finding 2 — reader ignores reported close failures

**Status: reproduced and handed to root/the agent assigned `spatialBundleUtil`; not changed by this agent.**

The three spatial read helpers (`readJson`, `readPlane`, `hashFile`) only close through `onCleanup(@()closeQuietly(fid))`. `closeQuietly` ignores both a nonzero `fclose` status and exceptions. Successful reads therefore do not report close failures even though the artifact contract requires truthful close-failure reporting. The writer already explicitly checks its close status.

`w06_c_io_probe.m` creates one small ordinary bundle, copies it, and shadows `fclose` only for `input.f64`. The hook physically closes the handle and then returns `-1`. This isolates error-status handling from leaks or permission failures. On a complete read, two injected failures occurred (hash and payload reads), but the reader returned successfully with `threw=false`. The identical hook on export produced one failure and correctly raised `ALEV4:SpatialWriteFailed`, removed its owned stage and left the target absent.

Observed values:

```json
{"case":"reader_close_returns_failure","threw":false,"error_identifier":"","injected_close_failures":2,"rng_preserved":true,"handles_preserved":true}
```

```json
{"case":"writer_close_returns_failure","error_identifier":"ALEV4:SpatialWriteFailed","injected_close_failures":1,"destination_absent":true,"rng_preserved":true,"handles_preserved":true}
```

The suggested scope is explicit successful-path close/status checks in the spatial read helpers, retaining quiet cleanup for already-failing paths. This report does not claim a spontaneous operating-system close failure was observed.
