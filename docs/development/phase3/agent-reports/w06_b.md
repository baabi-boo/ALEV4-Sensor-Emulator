## Fixed defect: portable informational metadata

### Reproduction before the fix

Using `make_overlap_bundle` to create a temporary handwritten valid bundle, replacing only its optional `spatial_provenance` with each of the following was accepted:

| Mutation | Before fix | Current result |
| --- | --- | --- |
| `{"bad-key": 1}` | Accepted | Rejected: portable field spelling |
| `{"for": 1}` | Accepted | Rejected: reserved keyword |
| A 64-character ASCII key | Accepted | Rejected: portable field spelling |
| `{"café": 1}` | Accepted | Rejected: non-ASCII key |
| An object with 257 distinct valid keys | Accepted | Rejected: 256-field bound |
| More than 64 nested JSON containers | Accepted | Rejected: nesting bound |

The native `decodeBundleJson.m` already rejects nonportable original keys, excessive object size, and excessive nesting. Its host-dependent `isvarname` and `namelengthmax` details are being frozen for Phase 3 by the separate native-parser owner. The previous Python `informational` walker validated values but only applied `text_value` to keys, leaving these key and container restrictions unenforced.

The exploit was also reproduced on a **temporary copy of actual development output**: adding `spatial_provenance["bad-key"] = 1` to `demo/iset_checker/spatial.json` left both `verify_bundle` and `verify_outputs(..., expected_commit=...)` passing before the fix. The manifest itself has no self-hash, and the ISET fixture permits informational provenance beyond its required labels. A byte-repeat check alone would not protect against matching malformed edits in both artifact sets.

### Implemented contract

All objects decoded by the Phase 3 `read_json` path now obey:

1. Keys match `[A-Za-z][A-Za-z0-9_]{0,62}` exactly, giving a fixed **63-character** ceiling.
2. Keys are not in the frozen **41-entry MATLAB / supported-Octave keyword union**.
3. An object contains at most **256 unique keys**. Duplicate/escaped-alias rejection still comes from the existing shared duplicate-key check.
4. Total nesting is at most **64 containers**. The outer manifest object counts as one; every object and array contributes another level, including vector and matrix arrays.

The frozen keyword set is:

```text
__FILE__ __LINE__ break case catch classdef continue do else elseif end
end_try_catch end_unwind_protect endarguments endclassdef endenumeration
endevents endfor endfunction endif endmethods endparfor endproperties
endspmd endswitch endwhile for function global if otherwise parfor
persistent return spmd switch try until unwind_protect
unwind_protect_cleanup while
```

Agent 6a obtained this actual list from the available Octave 9.4.0 runtime and confirmed that it includes every standard MATLAB keyword. `__FILE__` and `__LINE__` additionally fail the first-letter grammar. The contextual names `enumeration`, `events`, `methods`, and `properties` remain allowed and have positive controls; the initial Octave manual listing was not a reliable replacement for the executed `iskeyword()` result. Root and Agent 6a agreed on this exact frozen set.

Primary language references inspected were [MATLAB iskeyword](https://www.mathworks.com/help/matlab/ref/iskeyword.html), [MATLAB isvarname](https://www.mathworks.com/help/matlab/ref/isvarname.html), and [Octave 9.4 keywords](https://docs.octave.org/v9.4.0/Keywords.html). MATLAB's current documentation reports that the host identifier maximum increased in R2025a; the fixed 63-character wire ceiling deliberately avoids changing artifact acceptance with the host runtime.

## Independent mathematical checks

No native numerical producer was used for the following handwritten controls; the fixture writer only serialized supplied literal arrays.

### Nonuniform two-dimensional overlap and CFA spectral conversion

A one-pixel target covers `x=[0,1]`, `y=[0,1]`. Source edges are `x=[-0.25,0.25,1.5]`, `y=[-0.5,0.5,1.25]`, giving normalized x-weights `(0.25,0.75)` and y-weights `(0.5,0.5)`. The two source planes, in row-major order, are `(2,6,10,18)` and `(5,9,1,13)`.

The independently calculated averages are:

```text
plane 1 = 2/8 + 18/8 + 10/8 + 54/8 = 10.5
plane 2 = 5/8 + 27/8 + 1/8 + 39/8 = 9
```

For the red pixel, widths `(2,3)`, QE `(0.25,0.5)`, exposure `0.5`, pitch `1`, and fill factor `0.5` give collection `0.25` and charge:

```text
0.25 * (10.5 * 2 * 0.25 + 9 * 3 * 0.5) = 4.6875 electrons.
```

Gain `2` and black `0.25` give rounded RAW code **10**. The verifier returned exactly `[10.5,9]`, `[4.6875]`, and `[10]`.

### Vertical asymmetric 3-by-2 PSF with origin (3,1)

The first input plane is the 4-by-3 matrix containing `1..12` in row-major order; the second plane is three times the first. The shared kernel is:

```text
[1/8 1/4; 0 1/4; 1/8 1/4]
```

Its origin is `(3,1)`. Valid-support physical cropping yields `x=[1,2,3]`, `y=[0,1,2]`. For the first output:

```text
8/8 + 7/4 + 0*5 + 4/4 + 2/8 + 1/4 = 4.25.
```

The first optical plane is therefore `[4.25,5.25,7.25,8.25]`; the second is `[12.75,15.75,21.75,24.75]`. Applying the same explicit two-bin small-sensor configuration and RGGB parity gives expected electrons `[5.3125,10.171875,14.046875,21.65625]` and RAW `[11,21,28,44]`. The verifier accepted exactly those values. This separately checks convolution reversal, an origin at a kernel corner, valid crop coordinates, spectral-plane ordering, and CFA mapping.

## Deferred enhancement: shot-only dual support consistency

A separate temporary fixture sets `shot_noise=true` and both electronic read-noise amplitudes to zero. The high path has gain/black `(8,2)`, and the low path `(2,1.5)`.

The existing general verifier accepts the internally merged/flagged observations:

| High code | Low code | Merged electrons | Flags | Additional physical inconsistency |
| --- | --- | --- | --- | --- |
| 202 | 4 | 25 | 224 | High implies stored charge in `[24.9375,25.0625)`; low implies `[1,1.5)`. Their intersection is empty. |
| 0 | 32 | 15.25 | 192 | With zero read noise and nonnegative stored charge, high code cannot fall below the rounded black minimum of 2. |

The mutated bytes, merge values, and flag bytes were rehashed in the temporary manifests. They satisfy the checks currently performed: code range, observable merge reconstruction, conservative usable-channel flags, and clipping implications. They cannot arise from one noiseless-electronics shared charge, regardless of the Poisson realization.

An interval-intersection check could prove this impossibility without regenerating the random stream. However, the explicit current reader boundary does **not** promise to establish every possible stochastic analog history; the unchanged Phase 2 verifier has the same scope. The fixed noisy Phase 3 demo uses nonzero electronic read noise on both paths, so these altered zero-noise configurations cannot substitute for that required fixture. Root explicitly directed that this review retain the existing guarantees and treat stronger shared-charge support checks as a **future enhancement**, to be specified consistently for native and Python readers. No readout behavior, prior-phase production code, or readout guarantees were changed.
