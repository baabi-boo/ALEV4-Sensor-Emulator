## Confirmed finding and fix verification

**Output size validation originally occurred after target coordinate allocation.** In the reviewed version, `resampleSensorIrradiance` called `sensorGrid` before testing the output's 100-million-numeric-sample limit. `sensorGrid` constructs index, edge, and centre vectors. An invalid output request could therefore allocate large coordinate arrays before producing its expected validation error.

Bounded reproduction:

```matlab
input = ones(1,1,101);
grid = struct('x_edges_m',[0 1000000],'y_edges_m',[0 1]);
geometry = struct('full_grid_size',[1 1000000],'pixel_pitch_m',1);
alev4.resampleSensorIrradiance(input,grid,geometry);
```

This tiny 101-sample input asks for 101,000,000 output samples, exceeding the declared limit. The expected error is `ALEV4:InvalidSpatialSampling`.

| Observed behavior | Before root fix | After root fix |
| --- | ---: | ---: |
| Expected validation error | Yes | Yes |
| `sensorGrid` calls before rejection, independently profiled | 1 | 0 |
| Allocated target x-edge / x-centre vector lengths | 1,000,001 / 1,000,000 | 0 / 0 |
| Elapsed sampled call | 0.076377 s | 0.005778 s |
| Fresh-process peak resident memory | 69,764 KiB | 38,848 KiB |

The much larger case `[1 1e8]` with two spectral planes would request a prohibited 200-million-sample output while first constructing length-100-million coordinate vectors. That larger case was **not executed**; the extrapolation follows directly from the vector construction and guard order. No out-of-memory probe was attempted.

The root agent moved the output count check before `sensorGrid`, using the already validated `geometry.active_roi(3:4)` and band count. This reviewer reran the same bounded invalid request and asserted that `sensorGrid` was absent from the profiler. The check passed. The root agent is responsible for retaining its repository regression; this reviewer made no production change.

## Algorithm and physical-contract assessment

No wrong-density, wrong-region, spectral-crosstalk, crop-shift, or exact-copy defect was found in the executed cases.

The geometric operator returns density: target averaging divides overlap lengths by target widths on each axis, so the product is area divided by target area. There is no pixel-area, fill-factor, exposure, QE, or wavelength-bin multiplication in this helper. Constant-field preservation and joint coordinate-scaling invariance independently confirm that interpretation. The report's area-integrated units are photons/(s nm); independent crop conservation uses matching physical regions, including cases where the full-source integral is larger than the crop integral.

The moving source index traverses ordered cells monotonically. Each axis's positive overlap count is bounded by `ns + nt - 1` for the contiguous covered partitions. Sparse weight construction and its dynamically grown triplets therefore remain linear in source/target axis sizes rather than creating a dense source-by-target overlap matrix.

For a source of `Hs×Ws` and target of `Ht×Wt`, the selected separable intermediate has `min(Ht*Ws, Hs*Wt)` elements. Since the product of those two candidates equals `(Hs*Ws)*(Ht*Wt)`, the chosen intermediate is at most the geometric mean of source and target pixel counts. The same choice is used for the positive-support check. The two executed 20,000-cell orientations would otherwise expose a 400-million-element intermediate, approximately 3.2 GB for one double plane; the selected order needs one intermediate scalar per band for those fixtures.

The density cube limit remains a format/numeric support bound, not a memory guarantee. Optional integral diagnostics allocate dense area and term arrays at source or target plane size and repeat work per spectral plane. Validation, sparse triplets, coordinate vectors, reports, and temporary arrays also consume memory. This is a documented throughput limitation, not an additional demonstrated correctness defect. The newly fixed invalid-output case was avoidable because it should reject before those target vectors exist.
